## Open findings

1. **Comet 1.2.0 + Spark 4.2.0: a Python UDF over a Comet scan never completes.** Spark 4.2.0 added `spark.sql.execution.arrow.pythonUDF.columnarInput.enabled` (default `true`): `ArrowEvalPythonExec.supportsColumnar = child.supportsColumnar && conf.arrowPySparkUDFColumnarInputEnabled`, so it reads Comet's batches directly (`ColumnarArrowEvalPythonEvaluatorFactory`). With Comet's vectors (not `ArrowColumnVector`) the tasks wait forever in `PythonArrowOutput.read` and the Python workers sit idle (jstack taken during the hang: 16 task threads in `BasePythonRunner$ReaderInputStream.read`, under `ColumnarArrowEvalPythonEvaluatorFactory$...$anon$2.hasNext`). With the config `false`, it completes (`sum = 3999997`). Not established which side is wrong: Spark's columnar-input path (path 2 in the factory's doc comment, "Non-Arrow columnar readers ... reuse ColumnVector objects") or Comet's vectors/batch lifecycle. Not tried on Spark 4.3.0 (Comet does not start there). Repro: `code/ch47/repro_comet_udf.py` (venv-4.2.0, Comet 1.2.0 jar): writes `spark.range(1_000_000)` as Parquet, `select(udf(lambda x: x + 1)("x"))`, `sum`. Next step: run the same with an Arrow-backed DSv2 source and with Gluten/Auron on 4.2 to see whether only Comet hangs; then file against Comet first (it gives non-Arrow `ColumnVector`s), referencing the Spark config. Also check Spark 4.2.1.
2. **Binary breaks for third-party engines in 4.3.0 (not bugs, but a migration-guide gap).** (a) `spark.shuffle.manager` must now extend `private[spark] trait BlockingShuffleManager` (SPARK-58185): every external shuffle manager compiled for 4.2 fails at start (Comet, Auron shown; Gluten's `ColumnarShuffleManager`, RAPIDS', Celeborn's and Uniffle's would too). The error message suggests `spark.shuffle.manager.incremental`, which is misleading for a blocking columnar shuffle. Worth checking whether the 4.3 migration guide mentions it. (b) `StaticSQLConf.UI_RETAINED_EXECUTIONS` changed type to `ProtoBackedConfigEntry` (SPARK-56460, configs from text files): any jar compiled against 4.2 that reads a converted config entry gets `NoSuchMethodError`. (c) `FileSourceScanExec` gained `markedForSingleTaskExecution` (SPARK-57851). Not filed.
3. **Gluten 1.7.0 site:** the downloads page lists 1.7.0 as "Jun. 6, 2025", older than 1.6.0 (Mar. 10, 2026); the jar's build info says 2026-08-17. Likely a typo on the site. The chapter states no release date.
4. **Auron 9.0.0 ubuntu24 builder** installs JDK 8 but the spark-4.2 profile enforces JDK 17; `AURON_JAVA_VERSION=17` is honored only by images whose entrypoint switches JDKs (rockylinux8), and `docker compose` reuses the cached `docker-build-build-release` image across `--image` changes, so changing `--image` without removing the image silently keeps the old one.
5. **Benchmark pitfall that may affect other chapters:** calling `collect()` on the same DataFrame in a timing loop reuses its shuffle files and skips all stages but the last (`output/reuse.txt`: the second collect ran 1 stage, skipped 2, read 0 input rows). This chapter's first bench pass had this mistake (CPU `boroughs` "0.13 s"); it was thrown away. Other writers' `bench.py` scripts that loop over one DataFrame should be checked.
6. **Timing noise on the shared machine:** after the lock rule changed (only timed runs take the lock), unlocked films and scripts ran during the locked bench. The CPU on Spark 4.2.0 differed by up to 3x between passes. The chapter reports both passes and only claims speed-ups that hold in both. A rerun on a quiet machine would give cleaner numbers.
